# تصميم السقف الإجمالي لقسط — $10,000 لكل أموال العقد

> **الحالة:** تصميم للمراجعة فقط. لم يُعدَّل أي ملف Solidity، ولم يُنشر أو يُرقَّ شيء.
> **التاريخ:** 2026-10-01 · **العقد:** `MurabahaV6` (Proxy `0xb227…DEd5`، Build 21 حيّاً)
> **الاختبارات المرافقة:** `test/GlobalCap.design.test.ts` (موقوفة بـ`describe.skip` حتى التنفيذ)

## 0. لماذا لا يكفي `setLaunchCaps`

`maxPositionValueUSDC × maxActivePositions` يحدّ **دين المراكز** وحده. لا يغطّي:

- **أصول العروض غير المباعة:** `createOffer` و`increaseOffer` بلا أي حدّ.
- **الضمان الفعلي:** لا يقل عن 120% من الدين، والمشتري قادر يزيده بلا سقف (عند الشراء وعبر `addCollateral`).
- **ETH المعلّق للسحب** (`totalPendingETH`).

مثال: سقف $10k لمركز واحد. البائعون يودعون $500k في عروض، والمشتري يرهن $50k ضماناً لمركز دينه $10k. الأموال المعرّضة للخسارة عند وجود ثغرة تصير $550k تقريباً.

## 1. جرد كل الأموال التي يمسكها العقد

| الدلو | الأصل | يدخل عند | يخرج عند |
|---|---|---|---|
| **A. أصول العروض غير المباعة** | `offer.saleToken` (ETH/cbBTC) | `createOffer` · `increaseOffer` | `buy` (الكمية المشتراة) · `decreaseOffer` · `cancelOffer` |
| **B. ضمانات المراكز النشطة** | `position.collateralToken` | `buy` · `addCollateral` | `withdrawExcessCollateral` · اكتمال الأقساط · `earlyRepayCash` · `earlyRepayWithCollateral` · التصفية (`_settleByCollateral`) |
| **C. ETH المعلّق للسحب** | ETH | `_deliverToken` عند فشل الدفع المباشر أو لطرف ثالث | `withdrawETH` |
| **D. USDC/الستابل** | — | الأقساط والسداد المبكر | **في نفس المعاملة** (`transferFrom` ثم `transfer`) |
| **E. أرصدة شاردة** | ETH عبر `receive()`، رموز غريبة | تحويل مباشر خاطئ أو تبرّع | لا تخرج (ETH يُقفل؛ الرموز الغريبة عبر `emergencyWithdraw`) |

**دلو D:** الستابل يمرّ عبر العقد ولا يبقى فيه. لا رسوم USDC محتجزة، والرسوم تُدفع فوراً. الرصيد الحي **0 USDC**.

**دلو E غير محسوب عمداً.** هذه ليست مطالبات للمستخدمين. ولو حُسبت عبر `balanceOf` لصار ممكناً **إغراق السقف بتبرّع**: أي شخص يرسل cbBTC للعقد فيوقف كل الصفقات الجديدة.

**مطابقة الشبكة الحية (2026-10-01):**

| البند | القيمة |
|---|---|
| عرض #22 (ETH، نشط) | 0.005 ETH |
| عرض #24 (cbBTC، نشط) | 549,707 ساتوشي |
| مراكز نشطة | 0 |
| `totalPendingETH` | 0 |
| رصيد العقد الفعلي | 0.005 ETH · 549,707 ساتوشي · 0 USDC — **يطابق تماماً** |

### منع العدّ المزدوج

كل وحدة أصل تكون في **دلو واحد فقط** في أي لحظة، والانتقال بين الدلاء ذرّي:

- **الشراء:** `custody[saleToken] −= purchaseAmount`، وتخرج الوحدات للمشتري والخزائن (ETH للخزائن يدخل C بقدر الرسوم فقط). ثم `custody[collateralToken] += collateral`.
- **التصفية والإكمال:** `custody[collateral] −= x` **قبل** `_deliverToken`. إذا انتهى التسليم في C صار الأثر الصافي صفراً إلى أن يتم `withdrawETH`.
- **العرض الذي يُشترى:** يُنقص من A ولا يُحسب في B. الذي يدخل B هو الضمان، وهو أصل آخر جديد.

## 2. التصميم

### 2.1 التخزين: يُلحَق في النهاية بعد `maxActivePositions`

```solidity
/// @dev وحدات كل رمز محتجزة لحساب المستخدمين: عروض نشطة غير مباعة + ضمانات مراكز نشطة.
///      ETH المعلّق محسوب سلفاً في totalPendingETH — لا يُكرَّر هنا.
mapping(address => uint256) public custodyOf;
/// @dev سقف القيمة الإجمالية بالـUSDC (6 خانات). 0 = معطّل.
uint256 public globalCapUSDC;
```

**الثابت I1:** لكل رمز t، `custodyOf[t] = Σ saleAmount(عروض نشطة بـt) + Σ collateralAmount(مراكز نشطة بـt)`.

**الثابت I2:** `balanceOf(t) ≥ custodyOf[t] + (t == ETH ? totalPendingETH : 0)`، والفرق هو الأرصدة الشاردة فقط.

### 2.2 حساب الإجمالي بالدولار

```solidity
function totalExposureUSDC() public view returns (uint256 total) {
    for (uint256 i; i < tokenList.length; ++i) {
        address t = tokenList[i];
        uint256 units = custodyOf[t] + (t == address(0) ? totalPendingETH : 0);
        if (units != 0) total += _tokenValueUSDC(t, units);   // Chainlink + فحص Sequencer + رفض السعر القديم
    }
}
```

- `tokenList` يحتوي كل رمز سُجّل يوماً، بما فيها الرموز المعطّلة، فلا تسقط عهدة رمز أُطفئ لاحقاً.
- الرمز الذي عهدته صفر **لا يُقرأ سعره**. بهذا لا يوقف مغذٍّ معطّل رمزاً غير مستخدم.
- n صغير جداً (3 رموز اليوم)، فتكلفة الغاز محدودة.

### 2.3 فرض السقف على الالتزامات والإيداعات الجديدة

```solidity
function _enforceGlobalCap() internal view {
    uint256 cap = globalCapUSDC;
    if (cap == 0) return;
    uint256 exp = totalExposureUSDC();
    if (exp > cap) revert Errors.GlobalCapExceeded(exp, cap);
}
```

يُستدعى **في نهاية** الدوال التي تزيد العهدة فقط، **بعد** تحديث العدّادات. كل شيء يتراجع إذا فشل الفحص.

| الدالة | تغيير العهدة | فحص السقف |
|---|---|---|
| `createOffer` | `+amount` (saleToken) | ✅ |
| `increaseOffer` | `+added` | ✅ |
| `buy` | `−purchaseAmount` (sale) و`+collateral` (col) | ✅ على **الصافي** |
| `addCollateral` | `+added` | ⚠️ سياسة الإنقاذ (2.5) |
| `decreaseOffer` / `cancelOffer` | `−` | ❌ لا يُفحص أبداً |
| `withdrawExcessCollateral` | `−amount` | ❌ |
| `_chargeInstallment` (إكمال) | `−col` | ❌ |
| `earlyRepayCash` | `−col` | ❌ |
| `_settleByCollateral` (سداد بالضمان والتصفية) | `−collateral` | ❌ |
| `withdrawETH` | (C ينقص عبر العدّاد القائم) | ❌ |

**عبر عدّة مستخدمين وصفقات:** الفحص على **الإجمالي المشترك** في التخزين، لا على المستخدم أو الصفقة. الـEVM ينفّذ المعاملات بالتتابع، فكل معاملة ترى ما أودعته المعاملات السابقة. لا يمكن تجاوز السقف بتوزيع الإيداع على محافظ أو صفقات، ولا توجد نافذة سباق.

### 2.4 بقاء الخروج متاحاً دائماً

- **دوال الخروج لا تستدعي `_enforceGlobalCap`.** لو كانت الأسعار فوق السقف، السداد والسحب والإلغاء والإغلاق تبقى تعمل.
- **الإنقاص مُشبَع (saturating)** مع حدث تشخيص، على نهج `totalPendingETH`. لو حصل خطأ محاسبي فإنه **لا يحبس** أموال المستخدمين بـunderflow:
  ```solidity
  function _custodyOut(address t, uint256 x) internal {
      uint256 c = custodyOf[t];
      if (x > c) emit CustodyUnderflow(t, c, x);   // يكشف خللاً في I1 دون أن يُفشل الخروج
      custodyOf[t] = x > c ? 0 : c - x;
  }
  ```
- **حالة الإيقاف (`pause`) لم تتغيّر:** `payInstallment` و`earlyRepay*` و`withdrawExcess` محكومة اليوم بـ`whenNotPaused`، و`cancelOffer` و`decreaseOffer` و`withdrawETH` غير محكومة. السقف لا يضيف أي قيد على الخروج.

### 2.5 إضافة ضمان لحماية مركز قائم: «سماح الإنقاذ»

المنع المطلق خطير: بعد ارتفاع الأسعار قد يتجاوز الإجمالي السقف، فيعجز مدين عن إنقاذ مركزه ويُصفّى. والسماح المطلق ثغرة: يصير `addCollateral` بوابة إيداع بلا حد.

**التوصية:** `addCollateral` يمرّ دون فحص السقف **إذا** كان عامل صحة المركز بعد الإضافة ≤ `RESCUE_HF_BPS` (مقترح **15000 = 150%**). ما يتجاوز ذلك يخضع للسقف كأي إيداع.

- الإنقاذ مسموح دائماً بما يكفي لإبعاد المركز عن التصفية (105%) بهامش واسع.
- لا يمكن «ركن» ضمان زائد فوق 150% حين يكون الإجمالي فوق السقف.
- **عند تعطّل الأوراكل** يفشل حساب عامل الصحة، فترفض `addCollateral`، أي أنها مغلقة عند الفشل (fail-closed). هذا آمن لأن **التصفية نفسها تحتاج السعر** (`_settleByCollateral` و`healthFactor`)، فلا يُصفّى مركز بسبب السعر أثناء التعطّل.
  ⚠️ **استثناء:** تصفية **التأخّر** تقرّرها المدة، لكن تسويتها تحتاج السعر أيضاً، فتتعذّر بدورها أثناء التعطّل.

**بديل للمراجعة:** إعفاء كامل لـ`addCollateral`. أبسط، لكنه يكسر معنى «السقف الإجمالي». غير موصى به.

### 2.6 الإدارة والقراءة

```solidity
function setGlobalCap(uint256 capUSDC) external onlyOwner;   // event GlobalCapSet(old, new)
function remainingCapacityUSDC() external view returns (uint256); // للتطبيق والموقع قبل المعاملة
error GlobalCapExceeded(uint256 exposureUSDC, uint256 capUSDC);  // في Errors.sol
event CustodyUnderflow(address indexed token, uint256 had, uint256 removed);
```

- **خفض السقف تحت الإجمالي الحالي مسموح.** يوقف الجديد ولا يمسّ القائم.
- `setLaunchCaps` يبقى **حدّاً لتركّز المخاطر**، لا سقفاً إجمالياً. التوصية: سقف إجمالي $10,000 مع `maxPositionValueUSDC` بحدود $2,500، حتى لا يستهلك طرف واحد كامل السعة.

## 3. الأسعار والأوراكل

| الحالة | السلوك |
|---|---|
| **ارتفاع الأسعار** | السقف يُفحص **عند الدخول فقط**. إذا ارتفع BTC 50% يصير التعرّض الحي حتى 1.5 × السقف **دون أي إيداع جديد**. لا تصفية قسرية ولا إعادة لأموال أحد. الإيداعات الجديدة تُرفض حتى يعود الإجمالي تحت السقف (بخروج أو هبوط سعر). |
| **هبوط الأسعار** | يتحرّر جزء من السعة تلقائياً. |
| **أوراكل متقادم أو Sequencer معطّل** | كل الإيداعات والالتزامات الجديدة تُرفض (fail-closed)، **بما فيها `createOffer`** الذي لا يحتاج سعراً اليوم. ⚠️ إذا كان مغذّي ETH متقادماً وعهدة ETH أكبر من صفر، يُرفض إيداع cbBTC أيضاً لأن الإجمالي لا يُحسب. |
| **الخروج أثناء التعطّل** | `payInstallment` و`earlyRepayCash` و`cancelOffer` و`decreaseOffer` و`withdrawETH` **تعمل** لأنها لا تحتاج سعراً. `withdrawExcessCollateral` و`earlyRepayWithCollateral` والتصفية **متعذّرة اليوم أصلاً** أثناء التعطّل. السقف لا يغيّر شيئاً هنا. |

**التوصية التشغيلية:** ضبط السقف بهامش لتقلّب السعر، أو مراقبة `totalExposureUSDC()` وخفض السقف عند الاقتراب. أقصى تعرّض فعلي ≈ السقف × (أعلى سعر ÷ سعر الدخول).

## 4. ما لا يضمنه السقف

1. **الأموال في محافظ المستخدمين عبر الموافقات (approvals).** التطبيق يطلب موافقة USDC **غير محدودة** (BUG-050). ثغرة في أي مسار `transferFrom` قد تسحب من محافظ المستخدمين ما يتجاوز السقف بكثير. **أهم ثغرة خارج نطاق السقف.** التوصية: موافقات بالمبلغ الدقيق خلال الإطلاق المحروس.
2. **ثغرة تتجاوز المحاسبة نفسها.** السقف يحدّ ما **يُودَع**، والخسارة القصوى هي **الرصيد الفعلي** للعقد. إذا وُجد مسار يُدخل أصولاً دون تحديث العدّادات، ينكسر I2. اختبارات الثوابت (invariant) تكشف ذلك، لكنها لا تثبت غيابه.
3. **المالك والترقية (UUPS).** مالك مخترق أو ترقية خبيثة ترفع السقف أو تتجاوزه. الحماية هنا: Safe 2-of-3، وTimelock 48 ساعة (مؤجَّل).
4. **الأسعار:** ارتفاعها (القسم 3) أو خطأ Chainlink نفسه.
5. **مخاطر الائتمان:** البائع الذي يخسر لأن الضمان لم يغطِّ الدين بعد انهيار السعر. هذه خسارة اقتصادية، لا أموال محتجزة يمكن سرقتها.
6. **الأرصدة الشاردة** (دلو E) غير محسوبة عمداً.
7. **احتلال السعة:** طرف يملأ السقف بعروض لا تُباع فيمنع غيره. لا سرقة هنا، لكنه تعطيل. يخففه `maxPositionValueUSDC` جزئياً. لو احتاج الأمر لاحقاً: سقف فرعي للعروض غير المباعة.

## 5. التوافق مع تخطيط تخزين UUPS والمراكز القائمة

- **متغيّران جديدان يُلحقان في النهاية** بعد `maxActivePositions`، بنفس نهج Build 18 وBuild 20. لا إعادة ترتيب ولا تغيير في أي `struct`، ولا يوجد `__gap` يتأثّر. يُتحقّق آلياً بـ`validateUpgrade` من OpenZeppelin مقابل Build 21.
- **الترحيل:** `initializeV3(uint256 capUSDC)` بـ`reinitializer(3)`، ويُستدعى عبر `upgradeToAndCall` **في نفس معاملة الترقية**. بهذا لا توجد لحظة تكون فيها العدّادات صفراً والعروض قائمة.
  - يمرّ على العروض `1..nextOfferId-1` النشطة: `custodyOf[saleToken] += saleAmount`.
  - ويمرّ على `_activePositionIds`: `custodyOf[collateralToken] += collateralAmount`.
  - حيّاً اليوم: 24 عرضاً ومراكز نشطة صفر، فالتكلفة زهيدة.
  - **النتيجة المتوقعة:** `custodyOf[ETH] = 5e15` و`custodyOf[cbBTC] = 549,707`. سكربت ما بعد الترقية يقارنها بالأرصدة الفعلية (I2) ويتوقف عند الاختلاف.
- **المراكز والعروض القائمة** لا يتغيّر شيء من شروطها. إذا ضُبط السقف تحت إجماليها، تبقى تعمل ويخرج أصحابها بحرية، ويُمنع الجديد فقط.
- ⚠️ **حجم العقد:** 23,277 من 24,576 بايت، والمتبقي 1,299 بايت فقط. التقدير الأولي للإضافة 1.0–1.6 KB، فقد **تتجاوز الحد**. الخيارات بالترتيب:
  1. حذف `initializeV2` (ترحيل خاص بـSepolia، والإصدار على Base تجاوزه).
  2. نقل `totalExposureUSDC` و`_enforceGlobalCap` إلى مكتبة خارجية (`external library`). تحتاج ربطاً عند النشر.
  3. خفض `optimizer.runs`.

  يُقاس الحجم فعلياً قبل اختيار أي خيار.
