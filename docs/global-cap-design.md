## 0. لماذا لا يكفي `setLaunchCaps`

`maxPositionValueUSDC × maxActivePositions` يحدّ **دين المراكز** وحده. لا يغطّي:

- **أصول العروض غير المباعة:** `createOffer` و`increaseOffer` بلا أي حدّ.
- **الضمان الفعلي:** لا يقل عن نسبة العرض، وأدناها **110%** (`MIN_COLLATERAL_RATIO_BPS`). والمشتري قادر يزيده بلا سقف عند الشراء وعبر `addCollateral`.
- **ETH المعلّق للسحب** (`totalPendingETH`).

## 1. جرد الأموال التي يمسكها العقد

| الدلو | الأصل | يدخل عند | يخرج عند | في السقف؟ |
|---|---|---|---|---|
| **A. عروض غير مباعة** | `saleToken` | `createOffer` · `increaseOffer` | `buy` · `decreaseOffer` · `cancelOffer` | ✅ |
| **B. ضمانات مراكز نشطة** | `collateralToken` | `buy` · `addCollateral` | `withdrawExcess` · الإكمال · `earlyRepay*` · التصفية | ✅ |
| **C. ETH معلّق** | ETH | `_deliverToken` (فشل الدفع المباشر أو لطرف ثالث) | `withdrawETH` | ✅ |
| **D. ستابل** | USDC | الأقساط والسداد | **نفس المعاملة** | — يمرّ ولا يبقى |
| **E. غير متتبَّع** | تبرّعات · ETH عبر `receive()` · رموز غريبة | تحويل مباشر | لا يخرج | ❌ يُعرض **منفصلاً** |

**منع العدّ المزدوج:** كل وحدة في دلو واحد فقط في أي لحظة، والانتقال ذرّي.

- **الشراء:** يُطرح من A الكمية المشتراة، ويُضاف إلى B الضمان. رسوم ETH للخزائن تدخل C.
- **التصفية والإكمال:** يُطرح من B **قبل** التسليم. إذا انتهى التسليم في C صار الأثر الصافي صفراً.

**الدلو E** يُعرض عبر `untrackedBalance(token) = balance − custodyOf − (ETH ? totalPendingETH : 0)` للمراقبة فقط، ولا يدخل في السقف. هذا يمنع إغراق السقف بالتبرّعات.

**مطابقة حيّة (2026-10-01):**

| البند | القيمة |
|---|---|
| عرض #22 (ETH، نشط) | 0.005 ETH |
| عرض #24 (cbBTC، نشط) | 549,707 ساتوشي |
| مراكز نشطة | 0 |
| ETH معلّق | 0 |
| `tokenList` | `[ETH, cbBTC, USDC]` بلا تكرار |
| رصيد العقد الفعلي | يطابق تماماً |

⚠️ **الترحيل لا يعتمد على هذه الأرقام.** يحسبها من التخزين وقت الترقية (القسم 6).

## 2. قائمة رموز فريدة وثبات الوحدات (جبتي #1)

**الخلل الحالي (مؤكّد بقراءة الكود):** `addSupportedToken` يرفض فقط الرمز **المفعّل**. إعادة تفعيل رمز معطّل تمرّ، و`_registerToken` يعيد `tokenList.push`. النتيجة: تكرار في القائمة، فتُعدّ عهدة الرمز مرتين.

**الإصلاح المقترح** في `_registerToken`:

```solidity
TokenConfig memory prev = tokenConfigs[token];
bool known = _isRegistered(prev);   // سُجِّل يوماً (فحص O(1) القائم)
if (known) {
    // إعادة تفعيل: الوحدات المحتجزة بعشريات prev — لا يجوز تغييرها
    if (prev.decimals != decimals || prev.isStablecoin != isStablecoin) revert Errors.InvalidParams();
    if (prev.chainlinkFeed != feed) emit TokenFeedChanged(token, prev.chainlinkFeed, feed); // قرار إداري معلَن
} else {
    tokenList.push(token);           // يُضاف مرة واحدة في عمر العقد
}
tokenConfigs[token] = TokenConfig({ chainlinkFeed: feed, decimals: decimals, isStablecoin: isStablecoin, active: true });
```

- **العشريات وطبيعة الستابل ثابتة** للرمز طوال عمر العقد، لأن العهدة القائمة محسوبة بها.
- **تغيير المغذّي مسموح** بحدث صريح، لأن ترحيل مغذّي Chainlink حاجة تشغيلية مشروعة. يعيد تقييم العهدة القائمة فوراً، وهذا مقصود ومعلَن.
- **دفاع إضافي:** `initializeV3` يتحقق أن `tokenList` بلا تكرار، ويرفض الترقية إذا وجد تكراراً. حالياً القائمة الحية فريدة.

## 3. التخزين: يُلحق في النهاية بعد `maxActivePositions`

```solidity
mapping(address => uint256) public custodyOf;     // A + B بوحدات كل رمز (C في totalPendingETH القائم)
uint256 public globalCapUSDC;                     // السقف الصارم لكل الإيداعات — 0 = معطّل
uint256 public commitmentCapUSDC;                 // سقف الالتزامات الجديدة (< globalCap) — الفرق = احتياطي الإنقاذ
bool    public accountingFault;                   // خلل محاسبي مكتشَف ⇒ إيداعات موقوفة حتى المصالحة
```

**الثوابت:**

- **I1:** `custodyOf[t]` = مجموع العروض النشطة بالرمز t + مجموع الضمانات النشطة به.
- **I2:** `balanceOf(t) ≥ custodyOf[t] + (t == ETH ? totalPendingETH : 0)`.

⚠️ I2 **لا يثبت** I1 (جبتي #5). إذا كان العدّاد ناقصاً تبقى I2 صحيحة. I1 تُثبَت **باختبارات الثوابت** (القسم 8) وبسكربت المصالحة. I2 تُفحص على السلسلة كقاطع دائرة إضافي.

## 4. الإجمالي والفرض

```solidity
function totalExposureUSDC() public view returns (uint256 total) {
    for (uint256 i; i < tokenList.length; ++i) {          // فريدة (القسم 2)
        address t = tokenList[i];
        uint256 units = custodyOf[t] + (t == address(0) ? totalPendingETH : 0);
        if (units != 0) total += _tokenValueUSDC(t, units); // Chainlink + Sequencer + رفض السعر القديم
    }
}

/// @param isCommitment true لمسارات الالتزام الجديد (عروض/زيادة/شراء)، false لـaddCollateral
/// @return exp الإجمالي بعد العملية (يستعمله addCollateral لقاعدة الإنقاذ)
function _enforceCap(bool isCommitment) internal view returns (uint256 exp) {
    if (accountingFault) revert Errors.AccountingFault();       // جبتي #2
    _checkSolvency();                                           // I2 لكل رمز بعهدة — قاطع دائرة
    uint256 g = globalCapUSDC;
    if (g == 0) return 0;                                       // معطّل كلياً — (0,0) فقط، انظر 4.0
    exp = totalExposureUSDC();
    if (exp > g) revert Errors.GlobalCapExceeded(exp, g);       // الصارم يُفرض على **كل** مسار دخول
    if (isCommitment) {
        uint256 k = commitmentCapUSDC;
        if (k == 0) revert Errors.NewCommitmentsPaused();       // CAP-V2-01: الصفر = إيقاف لا «بلا حد»
        if (exp > k) revert Errors.GlobalCapExceeded(exp, k);
    }
}
```

### 4.0 دلالة الصفر (CAP-V2-01)

| `globalCap` | `commitmentCap` | المعنى | الإعداد |
|---|---|---|---|
| 0 | 0 | السقف **معطّل كلياً** (الوضع قبل التفعيل) | مقبول |
| 0 | > 0 | متناقض | **مرفوض** في `setCustodyCaps` و`initializeV3` |
| > 0 | 0 | **الالتزامات الجديدة موقوفة**، والإنقاذ وحده مسموح حتى `globalCap` | مقبول، أداة تشغيلية |
| > 0 | 0 < k ≤ g | الوضع العادي | مقبول |
| > 0 | k > g | متناقض | **مرفوض** |

- `globalCap` يُفحص **مستقلاً وأولاً** في كل مسار دخول، فلا يقدر أي إعداد لـ`commitmentCap` يعطّله.
- **الصفر لا يعني «بلا حد» إلا إذا كان الاثنان صفراً.** بهذا تنغلق فجوة الحالة (10,000, 0).

- **`_checkSolvency`:** لكل رمز عهدته أكبر من صفر، `balanceOf ≥ custody (+pending)`. إذا سُحبت أموال بثغرة تتجاوز المحاسبة، **تتوقف كل الإيداعات تلقائياً**.
- **الحساب المشترك:** الفحص على الإجمالي المشترك في التخزين. الـEVM ينفّذ المعاملات بالتتابع، فتوزيع الإيداع على عدة محافظ أو صفقات لا يتجاوز السقف.

| الدالة | العهدة | الحدّ |
|---|---|---|
| `createOffer` · `increaseOffer` | `+` | `commitmentCapUSDC` |
| `buy` | `−` البيع · `+` الضمان | `commitmentCapUSDC` على الصافي |
| `addCollateral` | `+` | احتياطي الإنقاذ (القسم 5) |
| `decreaseOffer` · `cancelOffer` · `withdrawExcess` · الإكمال · `earlyRepay*` · التصفية | `−` | **لا فحص أبداً** |
| `withdrawETH` | C `−` | **لا فحص أبداً** |

### 4.1 الخلل المحاسبي يوقف الإيداع ولا يحبس الخروج (جبتي #2)

```solidity
function _custodyOut(address t, uint256 x) internal {
    uint256 c = custodyOf[t];
    if (x > c) {                        // مستحيل إذا صحّ I1 — وجوده = خلل
        accountingFault = true;         // يبقى حتى مصالحة محمية
        emit AccountingFaultDetected(t, c, x);
        custodyOf[t] = 0;
    } else custodyOf[t] = c - x;
}
```

- **الخروج يكمل دائماً:** المستخدم يستلم ماله، ولا يوجد revert بسبب underflow.
- **الإيداع والالتزام** يُرفضان بـ`AccountingFault` إلى أن تتم المصالحة. لم يعد ممكناً الإيداع على إجمالي ناقص.

**المصالحة** عبر `reconcileCustody(address[] tokens, uint256[] values)`، وشروطها كلها على السلسلة:

1. `onlyOwner` (الـSafe 2-of-3) **و`whenPaused`**.
2. **لقطة كاملة لا جزئية:** `tokens` يجب أن **يطابق `tokenList` حرفياً**، بنفس الطول ونفس الترتيب. هذا يرفض بشرط واحد:
   - القائمة الفارغة.
   - الرمز المكرّر.
   - الرمز الناقص.
   - الرمز الغريب.
   - اختلاف طول `values` عن `tokens`.

   لا تقدر مصالحة رمز واحد تعيد فتح الإيداع وعهدة رمز آخر ما زالت ناقصة.
3. كل قيمة تحقّق I2 مقابل الرصيد الفعلي، وإلا تُرفض **المصالحة كلها**.
4. القيم يحسبها سكربت `scripts/reconcile-custody.ts` من التخزين مباشرة (العروض والمراكز النشطة)، وهو نفس منطق `recomputeCustody` في الاختبارات. السكربت يطبع الفرق لكل رمز قبل التوقيع.
5. تمسح `accountingFault` **فقط بعد** نجاح كل ما سبق، وتطلق حدثاً لكل رمز بالقيمة القديمة والجديدة.

```solidity
function reconcileCustody(address[] calldata tokens, uint256[] calldata values) external onlyOwner whenPaused {
    uint256 n = tokenList.length;
    if (tokens.length != n || values.length != n) revert Errors.InvalidParams();   // فارغ/ناقص/زائد
    for (uint256 i; i < n; ++i) {
        address t = tokenList[i];
        if (tokens[i] != t) revert Errors.InvalidParams();                           // ترتيب/تكرار/غريب
        uint256 owed = values[i] + (t == address(0) ? totalPendingETH : 0);
        uint256 bal  = t == address(0) ? address(this).balance : IERC20(t).balanceOf(address(this));
        if (bal < owed) revert Errors.CustodyInsolvent(t, bal, owed);                // I2
        emit CustodyReconciled(t, custodyOf[t], values[i]);
        custodyOf[t] = values[i];
    }
    accountingFault = false;
}
```

**حدود الثقة:** على السلسلة، المصالحة تفرض I2 فقط. صحة I1 تعتمد على السكربت وتوقيعَي الـSafe. البديل: إعادة حساب على السلسلة بدفعات (paged)، لكنها تكلّف حجماً لا يتحمّله العقد (القسم 7). نعرضها خياراً للقرار.

## 5. احتياطي الإنقاذ داخل السقف (جبتي #3)

**السقف الصارم:** `globalCapUSDC = 20,000`. **لا إيداع من أي نوع** يتجاوزه، ولا استثناءات.

| الحدّ | القيمة المقترحة* | يحكم |
|---|---|---|
| `commitmentCapUSDC` | 17,000 | العروض الجديدة والزيادات والشراء |
| احتياطي الإنقاذ = الفرق | 3,000 | `addCollateral` فقط |
| `globalCapUSDC` | 20,000 | كل شيء — صارم |

\* القيم النهائية **بعد** اختبار السيناريوهات (اختبار #8). المعيار: أن يكفي الاحتياطي لرفع أسوأ مركز متاح من حدّ التصفية 105% إلى 150% عند `maxPositionValueUSDC` المختار.

**`addCollateral`:**

- إذا كان الإجمالي بعد الإضافة ≤ `commitmentCap`: مسموح دائماً، كإيداع عادي.
- إذا كان بين `commitmentCap` و`globalCap`: مسموح **فقط** إذا كان HF المركز بعد الإضافة ≤ **150%**. الاحتياطي للإنقاذ، لا لركن ضمان زائد.
- إذا تجاوز `globalCap`: **مرفوض دائماً**.

### 5.0 كفاية الاحتياطي لعدّة مراكز معاً (اختبار ضغط — مراجعة جبتي)

**القاعدة:** سعة الإنقاذ المتاحة = `globalCap − الإجمالي الحالي`. **تكبر تلقائياً حين يهبط سعر الضمان**، لأن قيمة الضمان المحسوبة في الإجمالي تهبط معه.

**السيناريو المحسوب (الحدود الحية):**

| البند | القيمة |
|---|---|
| المراكز | 3، دين كل واحد $4,000، ضمان ETH بنسبة 120% |
| ضمان المراكز | $14,400 |
| عروض غير مباعة | $2,500 |
| الإجمالي قبل الهبوط | $16,900 (≤ 17,000) |
| الإجمالي بعد هبوط ETH 12.5% (كل مركز HF 105%) | $15,100 |

**النتيجة حسب هدف الإنقاذ:**

| الهدف | الإضافة لكل مركز | الإجمالي بعد إنقاذ الثلاثة | النتيجة |
|---|---|---|---|
| HF 150% | $1,800 | $20,500 | ❌ الثالث يُرفض |
| HF 130% | $1,000 | $18,100 | ✅ الثلاثة |
| HF 120% | $600 | $16,900 | ✅ الثلاثة، وبهامش |

**مُقاس فعلياً على العقد الحالي** (2026-10-02): البداية $16,886 · بعد الهبوط $15,087 · بعد 130% للثلاثة $18,085 · الأول والثاني إلى 150% ⇒ $19,684 · الثالث يضيف $799 ⇒ **$20,483 > 20,000**.

**الخلاصة الصريحة:** الاحتياطي **لا يضمن** أن يبلغ كل المراكز 150% في نفس الوقت. يضمن، في هذا السيناريو، إخراج الكل من منطقة التصفية إلى 130%. المتغيّر الحاسم هو العروض غير المباعة، لأنها تشغل السعة ولا تهبط قيمتها مع الضمان إذا كانت بأصل مختلف. لهذا يرتبط الخيار (ب) في §9.6 (سقف فرعي للعروض) مباشرةً بكفاية الإنقاذ. يغطيه اختبار #8b.

### 5.1 حين يكون الإجمالي فوق السقف (ارتفاع سعر)

إضافة الضمان مرفوضة لأن السقف صارم. **مسار الإنقاذ البديل لا يحتاج سعراً ولا يزيد العهدة:** `payInstallment` و`earlyRepayCash` تُنقصان الدين فيرتفع HF. يغطيه اختبار #7b.

### 5.2 تعطّل الأوراكل ثم عودته (جبتي #3)

أثناء التعطّل:

- `addCollateral` مرفوض، لأن الإجمالي لا يُحسب.
- **التصفية متعذّرة أيضاً**، لأن `healthFactor` و`_settleByCollateral` يقرآن السعر.
- مسار الدين (`payInstallment` و`earlyRepayCash`) **متاح**.

⚠️ **الخطر المتبقي (لا نصفه بأنه «آمن»):** عند عودة السعر قد يصبح مركز قابلاً للتصفية في نفس الكتلة، قبل أن يتمكّن المدين من التعزيز.

**التخفيف الحالي:** خلال التعطّل يقدر المدين يسدّد الدين فيرفع HF مسبقاً.

**خيار للقرار، غير موصى به الآن بسبب الحجم:** «مهلة تعافٍ». تُخزَّن `lastPriceRecovery[token]`، وتُمنع تصفية **نقص الضمان** (لا تصفية التأخّر) لمدة N دقيقة بعد عودة المغذّي. تحتاج متغيّراً وتعديلاً في `isLiquidatable` وتشغيلاً من محرّك (keeper).

## 6. الترحيل وتوافق UUPS (جبتي #5)

- **التخزين:** 4 متغيّرات تُلحق في النهاية، بنفس نهج Build 18 وBuild 20. لا تغيير في `struct` ولا إعادة ترتيب. يُفحص بـ`validateUpgrade` مقابل مصدر Build 21 الحيّ، المحفوظ في `contracts/legacy/MurabahaV6Build21.sol` مع **بصمة bytecode** تُقارَن بالتنفيذ الحي `0x0C01…83A7` على السلسلة قبل الترقية.
- **`initializeV3(uint256 globalCap, uint256 commitmentCap)`** بـ`reinitializer(3)` **و`onlyOwner`**، وتُستدعى **حصراً** عبر `upgradeToAndCall` في معاملة الـSafe نفسها. النتيجة: ترقية ذرّية بلا نافذة تكون فيها العدّادات صفراً.
  1. ترفض إذا وُجد تكرار في `tokenList`.
  2. تمرّ على العروض `1..nextOfferId-1` النشطة: `custodyOf[saleToken] += saleAmount`.
  3. تمرّ على `_activePositionIds`: `custodyOf[collateralToken] += collateralAmount`.
  4. تفرض I2 لكل رمز، فترفض الترقية إذا كان الرصيد أقل من العهدة المحسوبة.
  5. **لا تفترض حالة اليوم:** تعمل مع مراكز مفتوحة وETH معلّق ورسوم معلّقة للخزائن. يغطيها اختبار #11 بحالة مركّبة.
  6. تطبّق قواعد §4.0 على قيمتي السقف، فترفض (0, k>0) وk > g.
- **اختبار الصلاحية معزول (CAP-V2-02):** رفض ترقية يجريها غير المالك لا يثبت أن `initializeV3` نفسها محمية، لأن `_authorizeUpgrade` يرفض قبلها. الاختبار #11c في بيئة الاختبار فقط:
  1. المالك يرقّي **بلا** تهيئة.
  2. غريب يستدعي `initializeV3` مباشرة، ويُتوقَّع **`OwnableUnauthorizedAccount` تحديداً**.
  3. المالك ينجح مرة واحدة.
  4. الاستدعاء الثاني يُرفض بـ`InvalidInitialization`.

  مسار الإنتاج يبقى ذرّياً عبر `upgradeToAndCall`.
- **حالة التهيئة:** يُقرأ `_getInitializedVersion` الحي قبل الترقية (الـProxy على Base هُيّئ بـ`initialize` = 1؛ هل استُدعيت `initializeV2`؟ **يُتحقّق ولا يُفترض**)، ويُختار رقم reinitializer أكبر منه.
- **`initializeV2` لا تُحذف تلقائياً** لتوفير الحجم (جبتي #6). حذفها قرار يأتي بعد قياس الحجم وإثبات حالة التهيئة.

## 9. ما لا يضمنه السقف

1. **موافقات المحافظ:** موافقة USDC غير المحدودة (BUG-050) **توسّع التعرّض خارج العقد**. ليست ثغرة سحب مثبتة، لكن أي ثغرة مستقبلية في مسار `transferFrom` لا يحدّها السقف. التوصية: موافقات بالمبلغ الدقيق خلال الإطلاق المحروس.
2. **ارتفاع الأسعار:** يُفحص السقف عند الدخول فقط. أقصى تعرّض ≈ السقف × (أعلى سعر ÷ سعر الدخول).
3. **ثغرة تتجاوز المحاسبة:** قاطع I2 يوقف الإيداع بعدها، لكنه لا يسترجع ما سُرق.
4. **المالك والترقية:** Safe 2-of-3. Timelock مؤجَّل.
5. **خطأ Chainlink نفسه**، ومخاطر الائتمان عند انهيار السعر.
6. **احتلال السعة:** بائع يملأ `commitmentCap` بعروض لا تُباع. `maxPositionValueUSDC` **لا يمنع هذا** لأنه يحدّ الدين لا العروض (جبتي #6). خيارات للقرار:
   - (أ) `maxOfferValueUSDC` لكل عرض: يُتجاوز بعدّة عروض أو محافظ.
   - (ب) سقف فرعي لمجموع العروض غير المباعة (مثلاً 50% من `commitmentCap`): يحمي سعة الشراء والضمان، لكنه لا يمنع بائعاً واحداً من ملء حصة العروض.
   - (ج) قبول المخاطرة مع مراقبة: مكلفة للمحتل لأن أصوله محجوزة، ولا سرقة فيها.

   **التوصية: (ب)**، والمالك يقدر يخفض السقف ولا يقدر يطرد عرضاً.
