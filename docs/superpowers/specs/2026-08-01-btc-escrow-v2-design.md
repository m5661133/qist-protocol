# BtcEscrowMurabaha v2 — سوق ثنائي الاتجاه بثلاث خطوات

> التاريخ: 2026-08-01 · الحالة: معتمد للتنفيذ
> يُلغي ويستبدل دورة حياة v1 المنشورة على `0x47Ce614E8D1EBd19d66f254c062bDDEA2F3e3103`

---

## ١. الهدف

بيع بيتكوين **حقيقي** بالأجل، مضموناً ببيتكوين **حقيقي** مرهون، بحيث:

1. **الطرفان سواء:** البائع ينشر عرض بيع، والمشتري ينشر طلب شراء. من أعجبه عرض الآخر قبِله.
2. **أقل خطوات ممكنة:** ثلاث خطوات لإتمام البيع، وثلاث معاملات بيتكوين لعمر الصفقة.
3. **قسط لا تتدخل إلا حَكَماً:** مفتاحها في الخزنة معطَّل تماماً في المسار السليم.

## ٢. الصورة الشرعية المعتمدة

بيع بالأجل: البائع يبيع بيتكويناً بثمن مؤجّل (تكلفة + هامش ربح ثابت بالـ USDC).
المشتري **يقبض المبيع فعلاً** في عنوانه الخاص عند تمام البيع — لا قبضاً حكمياً.
المشتري يرهن بيتكويناً **منفصلاً** لضمان السداد، محجوزاً في خزنة `2-of-3`.
بعد سداد آخر قسط يُفَكّ الرهن ويعود للمشتري.

قرارات ثابتة موروثة من v1:
- المشتري لا يستلم USDC إطلاقاً — بيع لا قرض (BE-08).
- عند التصفية: يُؤخذ من الرهن بقدر الدين والرسوم فقط، **والفائض للمشتري** (BE-06).
- مهلة سماح قبل التعثّر — رفق بالمدين.
- الربح ثابت لا يزيد بالتأخير.

## ٣. ما تغيّر عن v1 ولماذا

| v1 | v2 | السبب |
|---|---|---|
| المشتري وحده ينشئ الصفقة | الطرفان ينشئان | متطلّب المنتج: سوق ثنائي الاتجاه |
| `createDeal` ثم `publishDeal` | إنشاء واحد يَنشر فوراً | حذف خطوة بلا فائدة |
| المبيع يُودَع في الخزنة ثم يُنقل بتوقيع منسّق ذرّي | **المبيع يذهب من البائع لعنوان المشتري مباشرة** | يحذف أعقد قطعة في النظام، ويُنقص معاملات بيتكوين من ٤ إلى ٣ |
| ١٥ حالة | ١٣ حالة | تسقط `DRAFT` و`AWAITING_LENDER` و`COLLATERAL_CONFIRMED` و`AWAITING_FUNDING` |

**لماذا لا يمكن أن تكون خطوتين:** عنوان خزنة الرهن `2-of-3` يُشتقّ من مفاتيح الأطراف الثلاثة. مفتاح الطرف المقابل مجهول قبل القبول، فالإيداع مستحيل قبله. ولأن عنوان المشتري مجهول قبل قبوله، لا يستطيع البائع التسليم مسبقاً. إذاً لا بد أن يقع فعل واحد على الأقل بعد المطابقة من كل طرف.

**لماذا لا نجعل الخزنة `1-of-2` (البائع + قسط):** لأن قسط تصير حينها قادرة على أخذ المال منفردة — وصاية كاملة، تنقض وعد المنتج وتستدعي ترخيص حفظ أصول. مرفوض.

## ٤. الخطوات

| # | الخطوة | الفاعل | الطبقة |
|---|---|---|---|
| ١ | ينشئ عرض بيع (أو طلب شراء) — ومعه مفتاحه العام | المُنشئ | Base |
| ٢ | يقبل، ثم يودع الرهن في الخزنة | المشتري | Base ثم Bitcoin |
| ٣ | يرسل المبيع مباشرة لعنوان المشتري | البائع | Bitcoin |
| — | أقساط USDC | المشتري | Base |
| — | فكّ الرهن للمشتري | البائع + المشتري | Bitcoin |

معاملات بيتكوين: **٣** — إيداع الرهن، تسليم المبيع، فكّ الرهن. وهو الحد الأدنى: الرهن يدخل ويخرج (٢)، والمبيع ينتقل (١).

> ملاحظة: في اتجاه «طلب الشراء» ترتيب الخطوتين ٢ و٣ يبقى كما هو — المشتري هو من يودع الرهن دائماً، والبائع هو من يسلّم دائماً. المتغيّر الوحيد من أنشأ الصفقة.

## ٥. متى تتدخل قسط

| الحالة | التوقيعان | قسط؟ |
|---|---|---|
| فكّ الرهن بعد السداد الكامل | البائع + المشتري | ❌ |
| البائع لم يسلّم خلال المهلة | المشتري + قسط | ✅ حَكَم |
| المشتري تعثّر → تصفية | البائع + قسط | ✅ حَكَم |
| البائع اختفى وقت فكّ الرهن | المشتري + قسط | ✅ حَكَم |

قسط بمفتاحها وحده لا تحرّك ساتوشي في أي حالة على الإطلاق.

## ٦. آلة الحالات

```
                 createSellOffer / createBuyRequest
                              ↓
                           OPEN ──────────────► CANCELLED
                              ↓ accept
                    AWAITING_COLLATERAL ───────► CANCELLED
                              ↓ confirmCollateral (رهن كافٍ)
                    AWAITING_DELIVERY ─────────► CANCELLED (بعد المهلة)
                              ↓ confirmDelivery
                           ACTIVE ⇄ PAYMENT_OVERDUE ⇄ MARGIN_CALL
                              │           ↓
                              │      DEFAULT_PENDING → DISPUTED
                              │           ↓
                              │   LIQUIDATION_ELIGIBLE → LIQUIDATED
                              ↓ آخر قسط
                           REPAID ──► COLLATERAL_RELEASED
```

الحالات الثلاث عشرة بالترتيب: `OPEN(0) · AWAITING_COLLATERAL(1) · AWAITING_DELIVERY(2) · ACTIVE(3) · PAYMENT_OVERDUE(4) · MARGIN_CALL(5) · DEFAULT_PENDING(6) · DISPUTED(7) · LIQUIDATION_ELIGIBLE(8) · LIQUIDATED(9) · REPAID(10) · COLLATERAL_RELEASED(11) · CANCELLED(12)`

## ٧. الواجهة البرمجية

### الإنشاء
```solidity
struct Terms {
    uint256 cost;                  // تكلفة المبيع (USDC، 6 خانات)
    uint16  profitBps;             // هامش الربح
    uint8   totalInstallments;     // 1 = دفعة واحدة
    uint32  paymentInterval;       // ثوانٍ
    uint16  marginCallLtvBps;
    uint16  liquidationLtvBps;
    uint64  merchandiseSats;       // البيتكوين المبيع
    uint64  requiredCollateralSats;// الرهن المطلوب من المشتري
}

function createSellOffer(Terms calldata t, bytes calldata sellerBtcPubkey)
    external returns (uint256 dealId);

function createBuyRequest(Terms calldata t, bytes calldata buyerBtcPubkey, string calldata buyerBtcAddress)
    external returns (uint256 dealId);
```

### القبول
```solidity
// يملأ الطرف الشاغر. المشتري يقدّم مفتاحه وعنوان استلام المبيع؛ البائع يقدّم مفتاحه فقط.
function accept(uint256 dealId, bytes calldata btcPubkey, string calldata btcAddress) external;
```

### الشهادات (attestor فقط — تسجيل لا تحريك)
```solidity
function confirmCollateral(uint256 dealId, uint64 sats, bytes32 escrowDescriptorHash, bytes32 txid) external;
function confirmDelivery(uint256 dealId, uint64 sats, bytes32 txid) external;      // المبيع وصل عنوان المشتري
function confirmLiquidation(...) external;
function confirmCollateralReleased(uint256 dealId, bytes32 txid) external;
function updateCollateral(uint256 dealId, uint64 newSats, bytes32 txid) external;
```

### السداد والصحة والنزاع — كما في v1 بلا تغيير
`payInstallment` · `poke` · `previewHealth` · `raiseDispute` · `resolveDispute` · `cancel`

### التحقّق من المفاتيح والعناوين
- المفتاح العام: طوله ٣٣ بايت وبادئته `0x02` أو `0x03` (مضغوط) — يُرفض غير ذلك.
- عنوان المشتري: غير فارغ وطوله ضمن حدود معقولة. **العقد لا يتحقّق من صحة bech32** — التحقّق في التطبيق وفي `qist-btc` قبل البناء والبثّ.

## ٨. الضمان والمخاطر

- `LTV = الدين المتبقّي ÷ قيمة الرهن` (الرهن وحده — المبيع خرج للمشتري ولم يعد ضماناً).
- الرهن المطلوب يحدّده مُنشئ الصفقة في `requiredCollateralSats`، ويُرفض القبول إن كان LTV الابتدائي فوق `MAX_INITIAL_LTV_BPS = 8000`.
- الخطر الأساسي: **الدين بالدولار والرهن بالبيتكوين.** هبوط السعر يرفع LTV. تُدار عبر نداء الهامش ثم التصفية، والفائض للمشتري.
- مع كل قسط ينخفض الدين فتتحسّن النسبة تلقائياً.
- السعر من Chainlink BTC/USD على Base مع فحص L2 Sequencer (`PriceLib`) — بلا تغيير عن v1.

## ٩. مخاطر التسليم وحمايتها

| الخطر | الحماية |
|---|---|
| المشتري أودع الرهن والبائع لم يسلّم | `DELIVERY_DEADLINE` = يومان؛ بعدها أيّ طرف يُلغي، ويستردّ المشتري رهنه بتوقيع المشتري + قسط |
| البائع سلّم أقلّ من المتفق | `confirmDelivery` يرفض `sats < merchandiseSats`؛ تبقى الصفقة قابلة للإلغاء |
| البائع سلّم لعنوان خاطئ | العنوان مسجّل على السلسلة وقت القبول — الشهادة تُطابقه، ومسار النزاع مفتوح |
| قسط تشهد زوراً | الشهادة **لا تحرّك بيتكويناً**. لا يتحرّك ساتوشي إلا بتوقيعين حقيقيين على L1 |

## ١٠. الترقية والتخزين

- العقد UUPS، والمالك محفظة الناشر `0xef6F…c2e4` — الترقية بمعاملة واحدة.
- **`nextDealId == 1` أي صفر صفقات مكتوبة.** تغيير هيكل `Deal` آمن تماماً: لا مفتاح كُتب في الـmapping.
- ترتيب متغيّرات التخزين العليا **يبقى كما هو حرفياً**: `usdc · btcUsdFeed · sequencerFeed · attestor · arbiter · protocolTreasury · protocolFeeBps · nextDealId · deals · __gap`.
- شرط ما قبل الترقية: التحقّق أونشين من أن `nextDealId == 1`. إن صارت أكبر، تتوقف الترقية ويُعاد التصميم بترحيل.

## ١١. التطبيق (Flutter)

شاشات جديدة تحت `lib/features/btc_escrow/`:

| الشاشة | الوظيفة |
|---|---|
| `btc_market_screen` | سوق العروض والطلبات المفتوحة (`OPEN`) مع فرز وتصفية |
| `btc_create_deal_screen` | إنشاء عرض بيع أو طلب شراء — نموذج واحد بمبدّل اتجاه |
| `btc_deal_detail_screen` | حالة الصفقة الحيّة، تعليمات الخطوة التالية، الأقساط، LTV |
| `btc_deals_screen` | صفقاتي (بائعاً ومشترياً) |

الطبقة الخدمية: `btc_escrow_service.dart` — قراءات `getDeal/previewHealth/installmentDue` عبر RPC، وكتابات عبر المحفظة (`tx_service`).

قواعد الواجهة الملزمة (من `CLAUDE.md` للتطبيق): **لا يُعرض زر إلا إذا تحقّق شرط استدعائه في العقد.**

| الزر | الشرط |
|---|---|
| قبول | `state == OPEN && msg.sender != المُنشئ` |
| دفع قسط | `state ∈ {ACTIVE, PAYMENT_OVERDUE, MARGIN_CALL, DEFAULT_PENDING}` |
| إلغاء | `OPEN` (المُنشئ) · `AWAITING_COLLATERAL` (الطرفان) · `AWAITING_DELIVERY` (بعد المهلة) |
| رفع نزاع | `state ∈ {ACTIVE…LIQUIDATION_ELIGIBLE}` وطرف في الصفقة |

الجانب البيتكويني في هذه المرحلة **إرشادي**: التطبيق يعرض عنوان الخزنة والمبلغ المطلوب ورابط `mempool.space`، والإيداع والتسليم يتمّان في محفظة المستخدم (Blue Wallet). ربط `qist-btc` كخادم يأتي في مرحلة تالية خلف واجهة `BtcEscrowApi` واحدة.

## ١٢. الاختبار

- اختبارات Hardhat تغطّي: الاتجاهين، القبول ومنع قبول النفس، رفض المفاتيح غير الصالحة، عتبة LTV الابتدائية، رفض التسليم الناقص، دورة الأقساط حتى `REPAID`، مسار المهلة والإلغاء، نداء الهامش والتصفية بفائض، النزاع والتحكيم.
- الشرط: **كل الاختبارات تمرّ قبل أي ترقية.** لا استثناء.
- اختبار fork ضد Base الحقيقية لقراءة Chainlink — كما في v1.

## ١٣. ما هو خارج النطاق هنا

- تشغيل `qist-btc` كخادم HTTP وربط عقدة Bitcoin و attestor حيّ.
- توقيع HSM.
- التدقيق الخارجي (استراتيجية D-057) — **إلزامي قبل أي إطلاق عام**.

هذا المسار يبقى **تجريبياً بمبالغ صغيرة** حتى يكتمل التدقيق.
